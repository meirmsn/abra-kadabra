# PR

The PR is what the owner judges, on a phone (TARGET § L3 Review). The mechanical steps are the
scripts named here; run them, never retype them as shell. Code changes, in any round, are built
under `devshop:build` § 3; this skill only puts them on the PR.

## 1. The body

- Write it from `/opt/devshop-current/templates/pr-body.md`: the summary, a 2–3 sentence paragraph
  on what changed and why it matters, the Announcement in the app user's words (guidance: `ship.sh`
  checks the shape, the owner the words). Claim only what you have just read from the real signal
  (CI, the preview).
- From the build: the `STACKS:` line goes in the engineering details, the design review's line
  under Evidence; a conflict where the project won is said; **Changed after the go** lists the
  owner's answers or PR comments recorded in the spec.
- **Screenshots go on the PR, never only in chat:** for a UI change, one per core-flow step and
  state-table state at the final commit, light and dark;
  `/opt/devshop-current/scripts/pr-assets.sh <image>...` adds them to the branch without changing
  a file and prints the image lines for the template's table (a row per step or state: label,
  light, dark); exit 2: ask the owner. After a new commit, take and add them again.
- Keep per-round detail out of the body. It ends where the template ends, then a line `---` and
  the plain footer line `_Generated by [Claude Code](https://claude.ai/code)_`: without it, the
  platform appends a footer that links the session, which the project's rules ban; `ship` reports
  that link (exit 2).

## 2. Through the reviewer

- The title starts with a Conventional Commit type (`feat:`, `fix:`, `docs:`, `chore:`, …; `!`
  before the colon for a breaking change), then the observable change, in ≤ 72 characters: the
  project's `scripts/pr-title-check.py` checks it in `ship` and in CI.
- Run `/opt/devshop-current/reviewer/ship.sh --title "<title>" --body-file <body file>`. It checks
  the words have the template's shape, then only on the independent reviewer's pass does it push,
  create or update the PR (ready) with those exact words and post the verdict; it is the only way to
  a PR.
- Exit 1: fix what it lists, the words here, code under `devshop:build` § 3 (a spec change:
  `devshop:intent` step 5); commit, and run `ship.sh` again. Exit 2 or 3: ask the owner.
- Run it again after any change to code or words. With only the words changed, it reviews the
  words alone (W10.9.7).

## 3. Findings

- The reviewer's `low` findings don't block and aren't fixed on reflex. Log each in `FINDINGS.md`
  (the template's rules: match first, a sighting on a repeat) and list it under **Low findings**,
  as one commit that changes only `FINDINGS.md` and `ROADMAP.md`; run `ship.sh` again, which
  reviews the words only.
- With the PR's link (§ 4), list each row logged as `med` or `high` and each whose sightings just
  reached 3, and ask "roadmap or keep watching?". A "roadmap" before the approval moves it (row
  deleted, a `ROADMAP.md` entry quoting the answer) in a records-only commit, then `ship.sh`; after
  the merge, in a small roadmap PR. Nothing else is surfaced.
- Findings about the devshop: one fenced block of plain lines (what happened, where) for the owner
  to paste into a devshop session. They are never written in the project.

## 4. Tell the owner, then watch the PR

- Once the PR is ready, in chat: its link and its one-line summary.
- Subscribe the session to the PR's activity (`subscribe_pr_activity`). Its events wake the
  session: end the turn, never poll.

## 5. Approval ships, comments are answered (TARGET Review 7–8)

- The owner's approval of the PR's current head, with every required check green on it: squash-merge
  it without asking for a "merge" message, then say in chat that it merged. Checks still running: merge on their green event. Hold only when the approval or the
  chat says to wait, or for a concrete reason: say it and ask. A push after approval needs a new one.
- **After the merge, how the change went.** The merge ends the PR's subscription, so arm
  `send_later` 5 minutes ahead. At each check-in, read the session's cost (`get_session`:
  `external_metadata.usage.cost_usd`, else `unknown`) and run
  `/opt/devshop-current/scripts/change-metrics.sh post --pr <n> --cost <usd>`. Exit 3: the deploy
  comment isn't final yet, arm `send_later` 5 minutes ahead again (it gives up an hour after the
  merge). Exit 0: posted; say so in chat. Exit 2: say what it printed. Nothing waits on it.
- Every owner comment on the PR is addressed: build what it asks under `devshop:build` § 3, then this
  skill again; one that changes a decision or acceptance item is recorded in the spec as changed
  after the go (`devshop:intent` § 5). One you can't address (unclear, conflicting, or outside the
  change): build nothing for it and tell the owner in the session's chat what it needs from them. A
  comment that only asks a question is answered there too.
