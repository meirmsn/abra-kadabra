# Workflow: Idea to Deployed

The end-to-end devshop pipeline, from rough notes to production. Six steps wrap five skills (`/office-hours`, `/autoplan`, `/ak-spec`, `/ak-build`, `/ak-go-live`); the user gate sits between steps 5 and 6. This guide is operator-facing — for the in-feature implementation contracts the steps invoke, see the routing index at [`README.md`](./README.md).

Standalone skills (usable outside the pipeline): `/ak-status`, `/ak-handoff`, `/ak-spec`, `/ak-implement`, `/ak-pre-ship`, `/ak-tests-review`, `/ak-design-conformance`, `/ak-new-project`, `/ak-migrate-project`.

## Step 1: Write rough notes

Problem description + rough solution idea. Not a full spec — just enough to seed the conversation.

## Step 2: `/office-hours` (gstack)

Interviews you, challenges framing, produces a product design doc. Forces you to articulate demand, urgency, and scope.

## Step 3: `/autoplan` (gstack)

Runs CEO, design, and engineering review sequentially. Locks in architecture, edge cases, and decisions. Output: a gstack plan in `.gstack/projects/<slug>/`.

- **3b: `/design-shotgun`** (optional) — visual variants before spec. Use for UI-heavy features only. Approve one direction before proceeding.
- **3c: `/design-html`** (optional) — turns approved mockup into an HTML reference file. Claude builds React from this instead of interpreting a description.

## Step 4: `/ak-build` (devshop skill) — autonomous pipeline

One command after autoplan. Chains everything through PR creation, CI verification, and notification. Resumable if the session is interrupted. The pipeline runs in full by default — every phase, every task, no matter how small — and `/ak-build` asks via `AskUserQuestion` before deviating to a lighter flow rather than silently scoping itself down.

**Phase 0: Preview + decisions checkpoint** — the one interactive beat before
token-heavy work. Reads the roadmap section, design doc, and test plan for this
feature; produces a 3-section preview (decisions / scope / hierarchical tracker
simulation) for user approval. On approval, writes `specs/<name>/spec.md` as a
skeleton — provenance header, Sources list, and a fully-populated Decisions
section — and commits it on the feature branch so the user's judgment calls
survive a crash. Starts a live `TaskCreate` tracker mirroring the preview's
hierarchy (phases as rows; sub-units — Phase 2 tasks, Phase 3 findings,
Phase 5 fix-loop attempts — prefix their parent phase as `<Phase X> /
<sub-unit>` since the harness's task list is flat). Finally,
emits a remote-control nudge ("type `/remote-control` now if you want
phone/watch monitoring") right before spawning the first subagent — the last
main-context beat before autonomous work begins. On resume paths that skip
Phase 0, the same nudge fires once from Step 0 at the equivalent timing.

For decision rows that turn on **"does X work in version Y of Z"** —
framework resolution order, library defaults, API edge-case semantics —
Phase 0 runs the empirical test BEFORE the user approves. 30 seconds of
"actually compile this and grep the output" beats committing implementation
code against an unverified hypothesis and discovering it was wrong
mid-Phase 2. Full triggering signals + per-layer verification recipes:
`/ak-build § 0.2.5 Empirical-verify load-bearing decisions before locking`.

**Phase 1: `/ak-spec`** — reads the Phase 0 skeleton and expands it in place
into a full spec (Core user story, In scope, Screens, Data model, API
contracts, Tests, Task order, Gotchas, Acceptance plan). Preserves the
skeleton's Decisions section verbatim — does NOT re-resolve. Creates the
feature branch (`feat/<slug>` or `fix/<slug>`) if currently on main
(inherited from Step 0 — Step 0 picks the prefix by counting existing
`feat/*` vs `feature/*` branches; greenfield projects default to `feat/`
to match the conventional-commit short form), and flips the `PLAN.md`
Planned row for this feature into `## Active`. The `## Task order` section is the discriminator
the resume check uses to tell "skeleton" from "complete spec." METRICS.md
confirmation only fires when the Phase 0 skeleton didn't cover events
(rare — only on manually-seeded feature branches).

**New (Phase 1-B landing — Core user story requirement)**: every spec
produced by `/ak-spec` MUST include a `## Core user story` section — 2-4
imperative verbs describing the product's primary flow end-to-end, OR the
literal body `N/A — <reason>` for non-user-facing PRs (migration-only,
internal refactor). Gate 9 enforces that every verb has a matching artifact
at `specs/<feature>/qa-walk/verb-<N>-<slug>.{png,json}` proving the action
completed — missing / empty artifact blocks Gate 9 with a per-verb
diagnostic. The `N/A — <reason>` rationale is itself adversarially reviewed
at pre-ship time (`coreUserStoryNaReason` check-type): interpretive prose
("no visible UI change", "cosmetic only") fails; verifiable file/path
claims ("diff is `supabase/migrations/**` only", "no `.tsx` files modified")
pass — bare `N/A` with no rationale auto-fails. See
`/devshop/.claude/skills/devshop/spec/SKILL.md § Core user story` for the
template + examples, and `/devshop/.claude/skills/devshop/pre-ship/SKILL.md
§ Gate 9` for the enforcement contract.

**Body-consistency check between /ship and Phase 6.** Each post-/ship
commit that lands while CI is green runs a body-consistency sub-step
(`/ak-build § 5.3.5`) that checks the post-/ship range for scope-drift
signals — new test files, replaced hero / qa-walk evidence, bundled CI
workflow changes, new runtime files. When a signal fires, the agent
reads the current PR body and edits any narrative claim the signals
invalidate (Summary scope, Evidence methodology, Test plan rows). Closes
the gap between Phase 5.3's checkbox-only refresh and Phase 6's full
sweep — without it, multi-commit polish loops silently drift the body
out of sync with what's been committed.

**Synthetic-harness substitution at Gate 9 is forbidden.** A degraded local
Supabase stack (auth schema errors, missing migrations, runner unreachable)
must surface as `blocked` with the bootstrap script's fix recipe — not be
worked around by mounting the component on an unrelated page or stubbing
its data path with fixtures. The full contract + the lalista PR 53 incident
that codified it lives at `/devshop/.claude/skills/devshop/pre-ship/SKILL.md
§ No synthetic-harness substitution`; deliberate operator opt-out for
low-risk diffs uses `git config devshop.requireHealthyLocalStack never`.

**Phase 2: `/ak-implement`** — reads spec, decomposes into tasks, implements with tests. Confirms active branch against `PLAN.md § Active`. Logs judgment calls in `specs/<name>/tasks.md` § Decisions. Stuck protocol uses fresh-agent-per-attempt with a per-task `specs/<name>/task-attempts/T<N>.md` already-tried log: attempt 1 natural; attempt 2 fresh sub-agent reading the log; attempt 3 fresh sub-agent + spec re-read + devil's-advocate sub-sub-agent enumerating structurally-different tactics; PROPOSE SPLIT escape hatch routes through `AskUserQuestion` when the task is actually 2–3 latent sub-tasks. Attempt 3 fail still marks task blocked + pings user.

**Phase 2.5: Verification (devshop only)** — a fresh subagent with zero implementation context reviews the diff and tests that the changes work. Catches surface-level integration gaps the implementation agent can't see: format mismatches, stale cross-references, wrong file permissions, incomplete doc updates. Finds AND fixes issues directly, committing per fix. Exit artifact: `specs/<feature>/verification.log`. See `devshop-mode.md § Phase 2.5` for the full contract.

**Phase 3: `/ak-pre-ship`** — quality gates only (no shipping). A Phase 0 preflight runs first: verifies required tooling (Chromium for browser gates) and aborts the whole pre-ship with a `blocked` status if tooling is missing, so gates can't silently turn a missing tool into a cheerful "skipped". After preflight passes, the gates dispatch as **per-gate sub-agents in two ordered passes**: a Stabilize-HEAD pass (sequential — each gate may commit fixes that mutate HEAD; covers preflight + docs/metrics/rls/slow-job/fast-job-local/migration-rollback/changed-tests-local checks + responsive + `/simplify` + `/design-review` + `/qa` + hero shots), then an Analysis pass (parallel — read-only against the stabilized HEAD; covers docs-and-tests-review/`/review`/`/cso`/design-conformance/`/benchmark`/preflight-final/convention). Each gate sub-agent writes its findings to a per-file sink at `specs/<feature>/gates/<canonical-gate-name>.md`; the orchestrator concatenates the sinks into `review.md` after each pass. Per-gate dispatch isolates failure — a crashed sub-agent loses at most one gate's work — and lets the Analysis pass fire in a single tool-use turn. Gate naming: `(ak)` marks devshop-native gates (either a devshop-owned check or a devshop-authored skill like `/ak-tests-review`); bare names wrap gstack skills invoked verbatim. The canonical source of truth for gate ordering + scope is `pre-ship/SKILL.md § Gates (canonical order + named IDs)`.

Gates 2d + 2f together are equivalent to the standalone `/preflight` skill — they form the front-of-chain fast-fail floor (lint/typecheck/unit/build + targeted integration/E2E) so 5 min of deterministic checks don't get hidden behind 25 min of LLM ceremony. Gate 10b is the same `/preflight` re-run at end-of-chain, catching cross-gate interaction breakage that per-gate `test:unit` checkpoints miss (each code-changing gate self-verifies its own edits via unit tests, but integration/E2E regressions and `/simplify`+`/review`+`/cso`+`/design-review`+`/qa` composition breakage only surface in the final attestation).

1. `docs-check` (ak)
2. `metrics-check` (ak)
   2b. `rls-coverage` (ak) — when `supabase/migrations/**` or client API touched; mechanical check that every RLS-enabled table written by client code has a matching `CREATE POLICY` for the operation in use (catches the silent-zero-row class lalista PR 5 hit)
   2c. `slow-job-lifecycle` (ak) — regression guard for the active slow-job. Verifies the slow + changes jobs are uncommented, the `if:` predicate carries both `pull_request` and the runtime gate, the edge-runtime retry is wired, per-step `hashFiles()` empty-state guards are present, the `Start local Supabase` step is intentionally unguarded, and branch protection includes the `slow` context
   2d. `fast-job-local` (ak) — when `turbo.json` exists; runs `pnpm turbo run lint typecheck test:unit build` with per-step wallclock budgets (Layer 1 of `/preflight`). Mirrors CI's fast-job verbatim so deterministic failures (type errors, broken unit tests, lint regressions) surface here in ~1–3 min instead of after a CI round-trip
   2e. `migration-rollback-roundtrip` (ak) — when diff touches `supabase/migrations/**`; round-trips each migration's `-- ROLLBACK:` block against local Postgres (rollback apply + forward re-apply per migration). After all gates pass, hero screenshots are captured to `specs/<name>/hero/` (committed) for the PR body — see `FAQ.md § How are specs and pipeline artifacts organized?` for the hero vs evidence split.

Gate outcomes use four categories: `pass`, `findings (N) [fixed|pending]`, `n/a`, `blocked`. `/ak-build` refuses to advance to `/ship` on any `blocked` gate. **LLM-mediated gates (6 `/review`, 7 `/cso`, 8 `/design-review`, 9 `/qa`) cannot emit `n/a` — they use `blocked (n/a per scope: <reason>)` for scope exemptions instead, so the rationale is auditable.** See `pre-ship/SKILL.md § Outcome semantics § ` `n/a` ` is not legal for LLM-mediated gates` for the rule and `ak-build/SKILL.md § Phase 3 → Phase 4 handoff` for the orchestrator-side halt rung.

Every gate's report must also include a `## Dismissals` section (body `None` or a bulleted list of findings-with-rationale). Pre-ship aggregates these into a `## Router Summary` block at the top of `review.md` and — when any body is non-`None` — hands the rationales to an adversarial reviewer (`kit/scripts/adversarial-review.sh dismissalLog`) that rejects weak, generic, or out-of-scope justifications. Rejection fails the gate the same as any `findings (N) pending` outcome. The check-type also applies severity-weighted shims for structured-output gates like `/cso` (TENTATIVE findings auto-dismiss with a mechanical rationale, no LLM call). See `hooks.md § Dismissal Log` for the full gating rules, env-var escape hatches, and forward-compatibility with the Phase 4 Finding Router.

**Phase 4: `/ship`** (gstack) — merges base, runs tests + review (final verification), bumps VERSION, pushes, creates PR, auto-invokes `/document-release`. PR body is seeded per the checkbox conventions in `/devshop/.claude/skills/devshop/build/SKILL.md § PR body conventions` — image embeds use the private-repo-safe `https://github.com/<owner>/<repo>/raw/<branch>/<path>` form; checkboxes are left `[ ]` at creation and ticked incrementally at 5.3 and 6.

**Phase 4.1 — Product update section leads the PR body.** Phase 4.1 pre-composes three artifacts before `/ship` runs: the PR title, a `## Product update` section (both `### Headline (user-facing)` and `### Detail (team-facing)` sub-sections copied verbatim from `spec.md`), and a `## Engineering details` section (the historical `## Summary` shape, renamed). `## Product update` is the **first content after the H1** so a reviewer landing on the PR cold sees the product story before the eng narrative. The same blurbs flow downstream — Phase 5.6 routes Detail to BUILD-LOG `Summary:` and Headline to a new sibling `Headline:` field, `/ak-go-live` Step 6 uses Headline as the deployed-to-prod lede + Detail as context paragraph, and future CHANGELOG / release-notes automation aggregates Headlines across merged PRs. Single source-of-truth at `spec.md § Product update`; no surface composes its own copy. See `/devshop/.claude/skills/ak-spec/SKILL.md § Product update` for the authoring contract + forbidden-vocabulary rules for Headline.

**Commit + PR subject/summary style (Phase 4 + `/ak-merge-devshop`).** Both surfaces enforce the same readability rule: commit subjects and PR titles **describe the observable change**, not the implementation detail. Lead with a verb when there's one verb-y change (`skip`, `add`, `fix`, `tighten`, `rename`); noun-lists are fine for multi-unit commits (`feat: invite link + member mgmt + audit feed`). No internal jargon ("polish", "soak findings", "Phase 2 expansion") — drop the meta-narrative and name the underlying user- or code-facing fact. Subjects ≤ 72 chars (err shorter). PR/squash **bodies** open with a one-sentence TL;DR + 3-7 bullets — each one a concrete user-meaningful unit. Bullets first; prose only when a non-obvious decision needs framing, kept to 1-2 sentences. Don't write a paragraph and then re-summarize it as bullets — pick one. Test: would a teammate scrolling `git log` two months from now know what shipped without opening the diff? Canonical rules: `kit/docs/guide/conventions.md § Commit + PR Text Style` (devshop-owned — survives `gstack` upgrades). Squash-specific shape: `.claude/skills/devshop/merge-devshop/SKILL.md § Subject style` + `§ Why bullet-led summary, not paragraphs`. The rules are intentionally NOT inlined into `gstack/ship/SKILL.md` (upstream-owned, would be clobbered on sync); when `/ship` is invoked from `/ak-build` Phase 4, the wrapper handoff carries the reminder.

**Phase 4 ships the bookkeeping atomically.** Sub-step 4.0 composes the BUILD-LOG entry + removes the `PLAN.md` Active row + commits on the feature branch BEFORE 4.2's `/ship` push, so `/ship`'s push carries the bookkeeping commit in the same CI cycle as the rest of the PR. The historical shape ran this work at Phase 5.6 after CI was already green — that triggered a fresh ~5-min CI cycle for what was structurally a docs-only push, paid fixed-cost per PR regardless of diff size. Phase 4.0 elides it.

**Phase 5: CI watch + post-CI-green PR-body edits** — watches CI via `gh pr checks --watch` (5.1–5.2). On failure: 5.4 dispatches each fix attempt as a **fresh `Agent` sub-invocation** with a persistent `specs/<feature>/fix-attempts.md` already-tried log (Hypothesis / Tried / Why ruled out / Ruled out for next attempt per attempt). Each attempt reads the log first and cannot repeat a ruled-out approach without explicitly justifying why the prior ruling-out was wrong. Attempt 1 is log-based inference; attempt 2+ pulls run artifacts (trace.zip per failed test) before guessing. Max 3 fix cycles; 5.5 escalates via PR @mention if still failing. On CI green: ticks the corresponding `## Test plan` / `### CI gates` PR-body checkboxes with attestations like `green on <sha>` and preview-deploy URLs (5.3). 5.6 verifies Phase 4.0's `chore(build-log)` commit shipped on the branch — common path is a no-op; resume rungs where 4.0 didn't fire run 4.0's procedure here + re-watch the resulting CI cycle. The historic Phase 5.7 (re-watch after 5.6's bookkeeping push) was deleted with the elision; its "watch every push" guarantee is folded into 5.3's preamble (every subsequent push on the branch — polish-loop fixes, audit-fix commits, 5.6-fallback pushes — must be re-watched before Phase 6 attests the PR body's CI-green checkbox).

After 5.6 verification, two late gates close the post-pre-ship gap (commits that landed AFTER `/ak-pre-ship` Gate 5 audited the spec snapshot — `/ship` commits, the entire CI fix-loop, dogfood-driven polish iterations — would otherwise reach merge unaudited). **Phase 5.8** spawns a Sonnet subagent that invokes `/ak-check-docs-and-tests` (the audit-time orchestrator; dispatches `/ak-docs-review` + `/ak-tests-review` as two parallel `Agent` calls with per-file sinks under `specs/<feature>/gates/audit-N-{docs,tests}.md`, then concatenates) over `<pre-ship-sha>..HEAD`. The range is computed from the latest `## Audit N` section's `<!-- audited-at: <SHA> -->` stamp in `review.md` — typically Audit 1, written by `/ak-pre-ship` Gate 5 against the spec snapshot. The orchestrator appends a new `## Audit 2` section to that same `review.md` (single-file model — appended `## Audit N` sections in the same review.md, no separate `test-review-followup.md`). Step 1 first runs `kit/scripts/preship/audit-tracker-only.sh "$RANGE"` and short-circuits (exit 0, no scaffold, no sub-skill dispatch) when the range is tracker-only — so a doc-only / tracker-only delta does not manufacture an orphan `review.md` stub. High-severity findings halt; medium are recorded in `review.md` for reviewer eyes; low get mentioned without listing. 5.8's first move is a polish-loop CI sanity check — it enumerates every CI run since `pr.createdAt` via `gh run list` and halts if the latest is non-success (mechanical replacement for a load-bearing per-push-watch discipline). **Phase 5.9** spawns a refresh subagent that re-captures `/ak-pre-ship` Gate 4 + Gate 13 hero shots at HEAD, commits only when `git diff --cached` shows real changes — freshness-only, no halt path, the `### Evidence` block in Phase 6 reports `(refreshed)` / `(unchanged at HEAD)` / `(skipped via idempotence)`.

**Phase 6: Verify the PR surface** — validates that the PR body tells the truth and posts nothing; the gate-by-gate audit trail lives in the committed `specs/<feature>/review.md`. The final sweep has four parts: Part A (state-based checkbox reconciliation), Part B (evidence-on-disk for each `[x]`), Part C (manual-review item classification + auto-attest factual ones), and **Part D — Product update verification**. Part D pairs an automated claim-vs-diff cross-check (Gate B — parses `spec.md § Product update § Detail` into atomic claims, greps the diff for each claim's nouns, and flags Headline/Detail audience-shape mismatches) with an autonomous review (Gate A — reads both blurbs against the diff + Gate B findings and classifies into Accurate / Edit-and-self-resolve / Escalate, prompting the operator only on a genuine claim-vs-diff product-judgment mismatch the diff can't settle). Gate B is warn-not-block; Gate A is autonomous, mirroring Parts A/B/C. Phase 0 authored the blurbs from intent; Part D verifies they still describe what shipped after polish. Edits at Gate A flow back to `spec.md` so downstream surfaces (BUILD-LOG, Phase 7, `/ak-go-live` Step 6) stay in sync.

**Phase 7: Notify** — detects diff type (runtime vs docs-only) and prints a terminal handoff: runtime changes (`apps/**`, `packages/**`, `supabase/migrations/**`, `supabase/functions/**`) get a "run `/ak-go-live` next" hint; docs-only diffs explicitly say `/ak-go-live` is not needed. No PR comment is posted — the PR being open IS the notification. The terminal handoff tells the user the next step without re-opening the PR.

## Step 5: You review the PR

- Release notes (from `/ship`) + the committed `review.md` audit trail (from `/ak-build`)
- CI green + Vercel preview URL
- You merge or request changes

## Step 6: `/ak-go-live` (devshop skill) — autonomous deploy

One command after you approve the PR.

1. **Pre-flight** — verifies the PR is ready (CI green, no merge conflicts), then runs three pre-merge probes:
   - **Production health probe** — curls the production URL from `CLAUDE.md § Deploy Configuration` to catch pre-existing prod failures the about-to-land deploy might mask. Splits HTTP `000` (firewall-IP-rotation — devcontainer connectivity issue, prod is probably fine) from real `4xx`/`5xx` responses (genuine pre-existing prod issue → operator question). Codified from lalista PR 26 (trailing-newline `NEXT_PUBLIC_SUPABASE_URL` → SSR 500) and PR 28 (Vercel edge-IP rotation false-positive). URL extraction lives in a shared sourceable helper at `kit/scripts/lib/extract-prod-url.sh` so the probe and its Mode A escape hatch parse the production URL identically — single source of truth, no drift. On `000`, the first move is `sudo /usr/local/bin/refresh-allowed-ips.sh` + re-probe — rotation is the common cause and recurs post-merge, and the script re-adds the current edge IPs in one shot (it reads the host from `/etc/refresh-allowed-ips/production_url`, so it's a no-op only when that file is genuinely empty). Classify by reading that file with a plain `cat`, never `sudo cat`: where sudo is `NOPASSWD` only for the refresh script, `sudo cat … 2>/dev/null` returns empty on the password prompt and misreads a populated, world-readable file as empty — turning a real Mode C into a phantom Mode A/B (codified from home-os PR #43).
   - **Migration sequencing pre-flight** — when the diff touches `supabase/migrations/**`, classifies each touched file as additive (CREATE / ADD COLUMN with default) vs mutating (DROP / RENAME / ALTER TYPE / SET NOT NULL without default). Honors `specs/<feature>/spec.md § Migration Sequencing` if pre-declared; otherwise applies the heuristic. Pauses on mutating migrations without an explicit deploy plan, since the parallel-deploy race (Vercel vs `deploy-migrations.yml`) creates a ~30–60s window where prod runs new code against the old schema.
   - **Pending tasks pre-flight surface** — reads the merging PR's body (plus any legacy `## Pre-ship audit` comment on PRs that pre-date the comment's removal) via `gh pr view`, parses every `[ ]` checkbox grouped by section, and prints a "Pending tasks before live" view annotated `[manual]` (operator-action needed) / `[deferred]` (PR-review concern, post-merge) / `[!]` (CI checkbox `/ak-build` Phase 5.3's auto-marker should have flipped — bookkeeping skipped). Blocks the merge via `AskUserQuestion` only when `## Out-of-band deploy items` has unchecked items (those are deploy prereqs by definition); other surfaces are non-blocking reminders. Operator picks "Done — proceed" / "Pause" / "Skip — accept the gap." Closes the gap where today the operator must mentally cross-reference every pending checkbox in the PR body at deploy time. Management API integration that converts `[manual]` items like email-template push and allow-list verify into `[auto]` — the automation core — is deferred to a separate PR; see `kit/ROADMAP.md § /ak-go-live post-merge prod-config sync (Arm B — automation core)`.
2. `/land-and-deploy` (gstack) — checks CI green, merges, waits for deploy, verifies prod health. The merge to main triggers three parallel auto-deploys: Vercel (Next.js app), `deploy-migrations.yml` if `supabase/migrations/**` changed, `deploy-functions.yml` if `supabase/functions/**` changed. See `guide/conventions.md § Deploy Boundaries` for the backwards-compatibility constraints that follow from the parallel-deploy race (especially for schema-mutating migrations). Auth-config changes still ship manually. **Pre-check at Step 2.0**: working tree must be clean before `gh pr merge` fires — `--squash --delete-branch` runs `git checkout <base>` inside the gh process, and a leftover uncommitted artifact (e.g., a stale Phase 5.8 audit section) makes the local checkout fail AFTER the GitHub-side merge + branch deletion already shipped (irrecoverable state if you weren't expecting it). Step 2.0 surfaces the dirty file via `AskUserQuestion` with commit / stash / abort options. Codified from home-os PR #26 (2026-05-16).
3. **Step 2.5 — Rewrite PR-body image URLs to merge SHA** — after `/land-and-deploy` returns merged but before branch cleanup, `/ak-go-live § Step 2.5` reads the merged PR's body, repoints every `https://github.com/<owner>/<repo>/raw/<feature-branch>/<path>` URL to the same path under `/raw/<merge-commit-SHA>/`, and writes the rewritten body back via `gh pr edit --body-file -`. The rewrite logic lives in a shared sourceable helper at `kit/scripts/lib/rewrite-pr-body-urls.sh` so the forward fix and the catch-up backfill use the same function — single source of truth, no behavior drift. Closes the "image embeds 404 the moment `--delete-branch` runs" gap; the per-PR conventions in `/ak-build § Image embeds — private-repo safe` ship the pre-merge form unchanged so this step has something to repoint. Skip semantics: null `mergeCommit.oid` (operator did a non-squash merge) → warn-and-continue; zero `/raw/<head-ref>/` matches (PR has no embeds) → silent attesting pass without `gh pr edit`. **Catch-up coverage for PRs that pre-date this step**: run `bash kit/scripts/backfill-pr-image-urls.sh --owner <owner> --repo <repo> [--dry-run|--accept-history-rewrite] [--limit N] [--since YYYY-MM-DD] [--skip-edited] [--bodies-only]`. Default mode is `--dry-run`; mutation requires explicit `--accept-history-rewrite`. Per-run JSONL audit log under `${GSTACK_HOME:-$HOME/.gstack}/backfill-pr-image-urls/<UTC-ts>.jsonl`; each row has a `target` field that's either `body` or `comment:<id>`. Skips PRs with no head-ref / no merge-SHA / zero matching URLs. The `--skip-edited` flag is opt-in conservatism — it additionally skips PRs whose body was edited >5min after merge, on the theory that the operator may have manually fixed URLs. Default is OFF because pipeline auto-edits (Phase 5.3 CI checkbox marks; historical Phase 6 audit comments on PRs that pre-date the comment's removal) routinely trip the heuristic without ever touching image URLs — leaving conservatism on by default mis-suppresses the actual rewrite targets (codified after lalista PRs #60 / #61 were silently skipped on the conservative pass). The `--bodies-only` flag opts out of comment processing — by default the script ALSO rewrites issue comments authored by the gh-cli authenticated user (on older PRs, typically historical Phase 6 audit-trail comments that embed hero shots; current /ak-build no longer posts them). Comments authored by other users (reviewers, bots) are skipped regardless via the `not-our-comment` audit reason — the gh API only allows editing your own comments. One-time per project — re-runs on already-rewritten bodies + comments are all-skip (idempotent).
4. **Branch cleanup + PLAN.md / BUILD-LOG sanity check** — locally `git branch -D` the merged feature branch and `git remote prune origin`. Verifies `/ak-build` Phase 4.0 already removed the Active row from PLAN.md and appended the entry to BUILD-LOG on the feature branch before merge. Surfaces (does NOT auto-fix) if the close-out was skipped — Claude can't commit to main, so missing close-outs need a human-initiated commit.
5. `/canary` (gstack) — ~15 min post-deploy monitoring. If fail: stops, notifies with rollback info (no auto-rollback). Same HTTP 000 vs 4xx/5xx split as Step 1 applies for canary failures.
6. **Rollback checkpoint** — records the current Vercel deployment ID, the latest migration filename, and the current Git SHA every time (even on success), so a future rollback has the coordinates pre-staged in the conversation rather than having to be reconstructed.
7. **Structured reflection** — routes learnings to committed files (CLAUDE.md, guide docs, backlogs). Two distinct categories, both required: 5a project-side (conventions, gotchas, troubleshooting, decision log) and 5b devshop-side generalization (skill amendments, template fixes, conventions). Either may be empty — explicit "nothing this session" beats fishing for noise. **PR-only main projects:** when branch protection blocks direct commits to main, open a small focused docs PR (e.g. `docs/<feature>-reflection`) with just the reflection commit; the overhead is acceptable and main's history stays clean.
8. **Notify** — PR comment: "@username deployed. Canary: pass/fail. Rollback SHA: xxx"

## Feature tracking: PLAN.md, BUILD-LOG.md, tasks.md

Three artifacts at three different grains:

- **`PLAN.md`** (at project root, forward-looking) — `## Active` and `## Planned (vN)` tables at the feature/PR grain, scoped to one version at a time. The Planned header declares the current ROADMAP/PRODUCT-ROADMAP tier (e.g., `v0`); only items from that tier belong in Planned. When every row ships or is dropped, bump to the next tier and pull in new items. Source of truth for "what's being built right now, on what branch" and "what's next." Consumed by `/ak-implement` (resolves spec via Active row), `/ak-status` (surfaces both sections), `/ak-go-live` Step 2b (sanity check). Written by `/ak-spec` (flips Planned → Active) and `/ak-build` Phase 4.0 (removes Active row at ship; 5.6 is a verify-only fallback).

- **`BUILD-LOG.md`** (at project root, backward-looking) — append-only shipped entries, no sections, most-recent first. One rich entry per merged PR with branch/spec path/Headline/Summary/gate results. **`Headline:` field carries `spec.md § Product update § Headline` verbatim** (user-facing, marketing-grade — the CHANGELOG primitive future release-notes automation aggregates); **`Summary:` field carries `spec.md § Product update § Detail` verbatim** (team-facing, the future-me grain that BUILD-LOG scanners want). PR number comes through the squash-merge subject on `main`, not the entry body. Written by `/ak-build` Phase 4.0 on the feature branch before `/ship` pushes, so the entry ships as part of the original CI cycle. Phase 5.6 is a verify-only fallback for resume rungs where 4.0 didn't fire.

- **`specs/<name>/tasks.md`** (per-feature, live) — in-flight per-task status (reconciled against actual commits on resume — `tasks.md` stamps no SHAs). Written by `/ak-implement` as it progresses. This is how you resume an in-progress feature across sessions. On resume, `/ak-build` Step 0 does not trust the `done` markers alone: before an "all done" file can skip the implement phase, `kit/scripts/reconcile-task-commits.sh` checks the markers against git state (clean working tree plus at least as many implementation commits as `done` tasks). A mismatch — a `done` marker with no matching commit, or a dirty tree — re-enters Phase 2 instead of skipping ahead.

Multiple rows may live in `PLAN.md § Active` at once — parallel feature work is supported, one row per live branch.

## Plan-level changes (rescope, reorder, drop)

The plan is a living doc. When scope shifts:

- **Reorder Planned**: edit `#` values; commit message captures why.
- **Drop a Planned row**: delete it; commit message is the audit record.
- **Defer "maybe later"**: move the entry from `PLAN.md` to `PRODUCT-ROADMAP.md` — explicit signal that it's not next.
- **Rename a feature**: edit the Feature cell; rename the spec folder if the feature is already Active.
- **History**: `git log --follow PLAN.md` shows the full evolution.

No `## Deprecated` section, no status column — git log is the audit trail.

## Workflow variants

The main pipeline diagram shows the idea-to-deployed flow. In practice five variants of that flow exist, differing in where you enter the pipeline:

| Variant                        | Entry point                  | Plan-time steps                                                                                                                          | PLAN.md handling                                                                                                           |
| ------------------------------ | ---------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------- |
| **Idea → full app**            | Rough notes                  | `/office-hours` → `/autoplan` → seed PLAN.md with one Planned row per PR                                                                 | Planned rows initialized in build order; each `/ak-build` flips row → Active → (removed at ship, entry lands in BUILD-LOG) |
| **New feature (existing app)** | "Let's add X"                | Short `/office-hours` or skip → `/autoplan` scoped → add a Planned row                                                                   | `/ak-build` picks up the row and transitions it                                                                            |
| **Feature improvement**        | "Auth's error UX needs work" | `/autoplan` on the scoped improvement → add Planned row with a new spec folder name, Notes references the prior spec as `**Builds on**:` | Same transitions as a new feature; spec folder is new (original stays as a snapshot of what shipped)                       |
| **Bug fix**                    | Reported bug                 | `/investigate` for root cause → brief Planned row (Notes = "bug fix: X") → `/ak-build` on `fix/*` branch                                 | Row lives briefly; ships like any feature                                                                                  |
| **Urgent hotfix**              | Production incident          | Skip planning — branch, fix, PR, merge                                                                                                   | Optional: retroactive BUILD-LOG entry + PLAN.md row only if meaningful                                                     |
| **Devshop feature**            | PLAN.md row or ROADMAP entry | `/ak-build` auto-detects devshop mode (`GIT_ROOT=/devshop`) → reduced gate set → `/ak-merge-devshop`                                     | Same transitions; BUILD-LOG + PLAN closure fires at Phase 4.0, then `/ak-merge-devshop` handles merge + push               |

The pipeline machinery is the same across all variants — only the pre-pipeline planning depth varies. `/ak-build` doesn't care whether the Planned row came from `/autoplan` or from a one-line edit. When running on `/devshop` itself, `/ak-build` auto-detects devshop mode and adapts: reduced gate set (6 of 19 gates dispatched, 13 pre-composed carve-outs), `/ak-merge-devshop` replaces `/ship`, no CI watch or Phase 6 PR-surface verification. See `.claude/skills/devshop/build/devshop-mode.md` for the full devshop-specific pipeline.

Multiple features can be in flight at once — `/ak-build` and `/ak-implement` ask which one to resume if more than one line is active.

## Structured Reflection

After each feature ships, run structured reflection in two distinct categories. Both required; either can be empty (just say "nothing to capture this session" explicitly). The full prompt template lives in `/ak-go-live § Step 5` (5a + 5b); this is the workflow-level summary.

### Project-side (5a)

- What went well? What was surprisingly hard?
- New conventions, gotchas, calibration updates → project `CLAUDE.md`
- New troubleshooting entries → guide docs (troubleshooting section)
- Decision log entries → guide docs (decision log section)
- Did confidence calibration need adjustment? (New items for "proceed" or "stop and ask" in project `CLAUDE.md`)

Skip 5a entirely when the bug + commit message + spec docs already carry the context — don't add CLAUDE.md noise for self-evident lessons. The next time the same kind of issue hits, the symptom itself is the signal.

### Devshop-side generalization (5b)

Did the session surface anything that would generalize **beyond this project**? Categories in order of typical leverage:

- **Skill amendment** — `/ak-build`, `/ak-go-live`, `/ak-spec`, `/ak-implement`, `/ak-tests-review`, `/ak-pre-ship`. Operational rules belong in the skill where they fire (Tier 2), not just in conventions.md (Tier 3 — discoverable but not auto-loaded).
- **Template fix** — `template/` (or referenced from `/ak-new-project Step <N>`). Inherited by every new project on next setup.
- **New convention or extension** — `kit/docs/guide/conventions.md`. Pair with a skill amendment that fires the rule.
- **`/devshop/CLAUDE.md` Tier 1 entry** — for cross-cutting principles that need to be always-loaded regardless of which skill ran.
- **`kit/ROADMAP.md § v0 / v1`** — for work bigger than an inline edit, OR an audit/sweep that needs a focused session.

Most sessions produce zero devshop-generalizable lessons. That's fine — explicitly say "nothing this session" rather than fish for noise. The signal is high but the rate is low. The agent surfaces the question proactively (per `/devshop/CLAUDE.md § Implementation Approach`); the user picks which lessons to ship now vs file vs skip.

Lalista PR 26 (2026-04-26) is the calibration case study: 8 generalizations in a single session — firewall closure rule, trace.zip discipline, conventions audit + reviewer-reads-conventions ROADMAP entries, prod-curl probe, firewall-IP-rotation fallback, .trim() defense, CSP scheme handling, Realtime publication, WebKit hydration race, edge-runtime retry. All shipped to devshop within the session because the agent surfaced the prompt explicitly.

- Devshop friction or ideas → `kit/TODOS.md` (tactical) or `kit/ROADMAP.md` (strategic)

## Starting a New Project

Run `/ak-new-project` from any devcontainer (the devshop's own or an existing project's).

- **Phase A** creates a GitHub repo populated with the `template/` skeleton, auto-assigns a Supabase port offset from the devshop registry (`kit/notes/projects/*.md` frontmatter), runs `supabase init` with a 5-port sed pass + `additional_redirect_urls` fix, and derives `.env` ports.
- **Phase B** runs inside the new project's container for interactive setup (accounts,
  credentials, scaffolding, integrations, security).

The skill tracks progress in `/devshop/kit/notes/projects/<name>.md` (not in
the project repo — keeps project history clean). See
`.claude/skills/devshop/new-project/SKILL.md` for the full step-by-step process.

**Project-specific firewall domains** (Step 6) go in `.devcontainer/firewall-extra-domains` — a `[scaffold-once]` overlay file seeded from the template and locked to `root:root 644` on every container start so only the operator (with `sudo nano`) can edit. Editing `init-firewall.sh` directly is a silent-revert trap: it's `[locked]` template-managed and reverts on every start. See `guide/architecture.md § File lifecycle § Hybrid lifecycle`.

To adopt the devshop on an existing project, run `/ak-migrate-project` (skeleton —
see `kit/ROADMAP.md`).

**Context-aware guideline routing** (added 2026-05-11). `/ak-spec` Step 1.5 and `/ak-implement` Step 1 consult the routing index at [`kit/docs/guide/README.md`](./README.md) — a table keyed by trigger signals (file-globs, Decisions keywords, primitive imports) that points at the guide sections governing each pattern. **Two-layer read shape (refined 2026-05-11)**: routing matches are **additive on top of** `conventions.md`, not a replacement for it. | `/ak-merge-devshop`        | Land a devshop feature branch into main                                        | Phase 1 **rebases onto `$ANCHOR` BEFORE the audit** (`git rebase "$ANCHOR"` in Phase 1.0), so a stale-base worktree isn't audited against a diverged `origin/main..HEAD` two-dot range that manufactures phantom "revert" findings (codified from the 2026-05-28 `go-live-prod-url-extraction` merge); the audit (`/ak-check-docs-and-tests --range "$ANCHOR..HEAD"`, Phase 1.1) then reviews exactly the delta the squash will introduce to main. The Phase 1.0 rebase runs through `kit/scripts/virtiofs-rebase.sh`, which mechanizes the virtiofs phantom-rebase recovery ladder (reduced-stat retry → merge fallback, discriminating phantom from genuine conflict by unmerged-path presence) and returns only real conflicts to the caller. Squash on the feature branch follows (`git reset --soft "$ANCHOR"` → `git commit -F` — format spec in the skill; `$ANCHOR` auto-flips between `origin/main` and local `main` when local carries an unpushed release commit) + ff-merge main to the squash commit + push + delete feature branch local + remote. Between the soft-reset and the `commit -F`, Phase 2 runs an **unconditional gitleaks compensating gate** (`gitleaks protect --staged --redact`, cwd-pinned to `$WORKTREE_PATH` when set) on the staged squash delta — mirrors `.husky/pre-commit:29` so a secret can't reach `main` even from an off-convention worktree that skipped the recipe's `pnpm install` and never armed its in-worktree hooks; a finding halts before the commit. The rename-plus-symlink collision corner that abandons the squash for Phase 3's `git merge --ff-only` (which lands constituent commits with no staged delta) is covered by a sibling **history-scanning** gate — `gitleaks git --redact --log-opts "$ANCHOR..$BRANCH"` over the commit range about to land, cwd-pinned the same way — so the net is genuinely path-independent: `protect --staged` for the squash path, `gitleaks git` for the ff-merge path, both halting before the merge on a finding. Phase 1's audit **interactively pauses on medium-severity findings** (devshop equivalent of `/ak-build` Phase 5.8 post-polish re-audit) so spec-vs-delivery gaps surface BEFORE the squash ships; `DEVSHOP_AUDIT_MEDIUM_POLICY=proceed` env-hatch bypasses the pause for auto-mode flows. Phase 4.2's teardown runs as **separate Bash calls per step** to dodge DCG's `push-force-short` false-positive on chained `-f` flags. Squashing on the feature branch dodges `check-branch-not-main.sh` structurally, and ff-merge creates no new commit on main, so the skill is autonomous end-to-end. **Worktree-aware**: Phase 0.1 scans `git worktree list --porcelain` for a feature worktree ahead of `origin/main` when invoked from `/devshop` on `main`; Phase 2 routes git via the `GIT_CMD` **array** (`"${GIT_CMD[@]}"`, never a string — zsh, the Bash tool's shell, does not word-split an unquoted string var, so a string `GIT_CMD="git -C <path>"` execs a bogus binary and exits 127); Phase 1.1 drives the audit with an absolute `--feature-dir` + a resolved SHA range (`${ANCHOR_SHA}..${HEAD_SHA}`) so it stays correct even though the Bash tool resets cwd to `/devshop` between calls (a bare `cd`-into-the-worktree does not persist); Phase 4.2 tears the worktree down (`submodule deinit -f --all` + `git worktree remove --force`) before deleting the branch. Pass `--branch <name>` to disambiguate multiple in-flight worktrees. `--source-worktree <path>` pushes directly from a named worktree when `/devshop` is on an unrelated branch; after the push, `git fetch origin main:main` syncs the local `main` ref without switching branches. **Phase 2.5's full-suite gate computes its verdict from a `grep -c '^not ok'` count** (not from reading the suite output — a single buried `not ok` is invisible in a ~1500-line green tail) and halts with the failing test names on any failure. It **pins the suite to the resolved (absolute) worktree path and asserts the tested `HEAD` equals the squash commit both before and after the run** — halting if a parallel session flipped the checkout mid-flow, so a concurrent merge can't false-green a red branch onto main (mirrors the Phase 3 checkout-verification guard; codified from `1d343bf`, 2026-05-28). A pre-existing `origin/main` failure (unrelated to the feature branch) gets fixed on a separate `fix/` branch first rather than folded into the feature squash. Idempotent across phases. Replaces the manual `git merge --ff-only` flow. The Phase 1.0 rebase is **not the sole** base-divergence phantom remedy: Phase 0.4.5's dimension-(d) propagation-surface precompute fires BEFORE the rebase and got its own complementary three-dot fix (it diffs `origin/main...$BRANCH`, not two-dot, so a stale-base branch isn't flagged with phantom propagation surfaces origin/main changed since the fork point — codified `b174a11`); see `kit/docs/guide/hooks.md § Dual-surface check-types`. |

> **Skill autocomplete**: The `name` field in SKILL.md frontmatter drives `/` autocomplete,
> not the directory or symlink name. When adding or renaming a skill, set `name: ak-<skill>`
> in the frontmatter to match the desired slash command.
>
> **Skill layout convention** (load-bearing — required for autocomplete discovery):
> a new devshop skill has TWO entries on disk —
>
> 1. Real content at `/devshop/.claude/skills/devshop/<short-name>/SKILL.md`
>    (no `ak-` prefix in the directory name).
> 2. Symlink at `/devshop/.claude/skills/ak-<short-name>` →
>    `devshop/<short-name>` (relative target, matches peer pattern).
>
> The sync script `kit/scripts/sync/create-devshop-symlinks.sh` walks
> `/devshop/.claude/skills/*` looking for **symlinks only** (`if [ -L ]`),
> then propagates each one to `/workspace/.claude/skills/`. Real
> directories at the top level of `/devshop/.claude/skills/` are
> silently ignored — a real-dir skill works in `/devshop` sessions
> but never reaches `/workspace`. After adding a new skill, run
> `bash kit/scripts/sync/create-devshop-symlinks.sh /workspace` (or
> restart the container) to populate the workspace-side symlink.
