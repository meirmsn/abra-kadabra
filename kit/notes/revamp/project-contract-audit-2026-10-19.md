# Audit: what the devshop expects a project to provide (2026-10-19)

Read-only survey of the devshop at `origin/main` (3172195, plus the r6 branch where marked [r6]) and
the fixture at its `origin/main` (30c2b4c). The website has no clone here; its column comes from
`runtime/stacks/cloudflare/README.md` (CF) and the devshop's specs, LOG and FINDINGS. "Unknown"
means those say nothing.

## Verdict

There is no single model of what a project must provide. It is a set of per-feature
expectations, each enforced its own way, and the devshop decided that on purpose: D-08
(`kit/notes/revamp/DECISIONS.md:243-246`) builds "the capability contract … only when a real project
commits to a second stack", superseded by "no general capability contract up front".

The only machine-readable list is `runtime/project-files.txt` (9 entries): the files the devshop
places, not the names it relies on. Everything else is a hard-coded path tested at the point of
use, or a sentence in a skill, guideline or stack home.

Enforcement comes in five strengths:

1. Required CI (the only wall): only what the project's own `check-fast.sh` calls.
2. Session-start feedback: `ci-tiers-check.py` (the `ci.yml` shape); `project-files.py check`
   (devshop-owned copies, only when the project pins a release).
3. Tools that refuse to run (could-not-run): `review.sh`, `ship.sh`, `pr-assets.sh`, `secret-scan.sh`.
4. Optional probes, silently skipped when absent: `setup.sh`, `lint.sh`, `lint-file.sh`,
   `deploy.sh`, `pr-title-check.py`, `local-run.sh` [r6].
5. Prose only.

## Where two components expect the same thing differently

1. Starting the app locally: five answers ([r6] `scripts/local-run.sh`; ui.md "as CLAUDE.md or the stack home says"; CF and the fixture's `check-slow.sh` start `wrangler dev` inline; fixture README `npm run dev`; gstack's ports 3000/4000/8080). F-NEW-103.
2. No `DESIGN.md`: build's design review skips; the [r6] reviewer judges against tokens.
3. Lint: the spec and install/README say `check-fast.sh` runs `scripts/lint.sh` from the stack home; the template doesn't call it, new-project doesn't place it, CF never mentions it, pre-push treats absence as fine.
4. What a project holds: install/README "one file"; TARGET Shape 3 three files; PF places 9 and `init` 2 more. TARGET's "no devshop references in project trees" vs the seeds' "(the devshop's template…)" comments.
5. ui.md says the upgrade re-copies the UI checks; they aren't in PF, so it can't.
6. Pin type: `init` requires a release tag; dispatch accepts a SHA; the fixture pins a pre-release SHA and so never gets the v2.0.0 manifest's drift check.
7. Deploy record: 7 outputs in the template and CF; the fixture writes 1; nothing checks the announce/report jobs.
8. Setup: probed with `-x` by the template and session start; called unconditionally by the fixture; the fixture's deploy job runs `npm ci` instead.
9. Routes list: two names, "the same rule", nothing reads either.
10. AC naming: `AC-<n>` (template, prompt) vs `<spec> AC-<n>` (CF, F-NEW-92).
11. Test location: `tests` (template) vs `test/` + `tests/` (fixture).
12. Screenshots: ui.md's six files vs pr-body's per-step rows vs the fixture's committed `docs/screenshots/`.
13. Where the stack's session rules live: CF says the project's CLAUDE.md restates them; the seed has no slot; CF says the project's CLAUDE.md wins on conflict.

## What a new stack (Next.js on Vercel, iOS) would need that has no home

- Detection: no `detect` for `*.xcodeproj`, `Package.swift`, `vercel.json`; `nextjs-supabase` is a placeholder.
- CI template is Linux-only (`ubuntu-24.04`, linux gitleaks); iOS needs macOS runners, signing, simulators; `check-fast.sh` assumes bash and python3.
- Deploy contract assumes a web deploy with an https URL, rollback line and smoke check; TestFlight has none; Vercel deploys from its Git integration outside `deploy.sh`, with its own preview comment.
- Previews: "none — native: simulator screenshots" is in the PR template; nothing produces them.
- Reviewer: allowlist is npm-only; no `xcodebuild`, `swift test`, `pnpm`, `npx next`. [r6] browser needs HTTP on 127.0.0.1 and Playwright in `node_modules`.
- UI guideline and checks are web-only (widths, theme toggle, CSS tokens, Playwright). iOS "uses gstack's on-device review", with no guideline.
- Setup is npm-shaped; no CocoaPods/SPM/Xcode story; no Mac in cloud sessions.
- Supabase (pausing, RLS) has no home; only D1 rules exist.
- Production data, secrets, deploy facts: M4 bullets and TARGET promises only.
- A stack home proven by scaffolding in CI (TARGET Reach 5) is deferred; a new home would again be prose copied from a project (F-NEW-100).

## What an outside collaborator would miss without the devshop

- Rules that stay in the devshop: spec, PR-body, findings and roadmap templates and their rules (projects delete the rules comment); `pr-body-check.py`, `ship.sh`, the reviewer and its verdicts (in the session's `.git/devshop/reviews/`); the review guard, pre-push hook, per-edit lint, dcg.
- Knowledge the project depends on but doesn't carry: stack rules unless restated in CLAUDE.md (the fixture did; the seed has no slot); the UI guideline and what `DESIGN.md` is for; how to run locally; how to name tests; which files must not be edited (the `devshop` copies; PF lives in the devshop).
- Tools and meaning: gitleaks version and sha are only in ci.yml env, no local install script; `python3` for spec-check; what `.devshop-version` and the jobs mean; squash-only merging. No CONTRIBUTING or project `docs/README.md` seed.
- What works: a plain clone runs its own CI (new-project AC-3 proves it with `/opt/devshop*` hidden); `deploy-comment.mjs` is copied in.
